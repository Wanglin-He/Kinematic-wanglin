P0 把提示词变成能被机器检查的契约，P3 用数学量出资产做到没做到。 判分过程不调用任何模型——只有查表、点积、计数、距离。

一准备工作

这三件事不做完，一条检查也跑不起来。

1.1 契约从哪来

P3 不读提示词，只读契约。十份契约由人从每条记录的提示词逐句翻译而来， 在打开任何资产之前写完、哈希、提交（contracts/pilot/FROZEN.json， 提交时间早于任何一次评测）。同一份契约在该记录的全部评测里一个字不改。

这一步是整套系统里唯一还靠人的环节，必须说清楚。 判分链路是纯计算，但契约本身是从提示词写出来的文字。哈希防的是「看了资产再改契约」， 防不了「一开始就把提示词读错」。 已经发生过一次：钻床的提示词写 standard locking features（复数、没给数）， 契约写成 1 个锁柄，资产实际有 2 个。那是契约作者的错，不是资产的错。 所以流程必须是：起草 → 逐条签字 → 再冻结。十份契约目前还没有第二个人核过。

1.2 十个案例怎么选的

按机构类型配槽位，不随机抽——目的是让 KF1/KF2/KF3 三条都有东西可测：

棱柱抽拉 ×1空气炸锅（抽拉篮 + 两个按压键）
旋转开合 ×4摄像机翻转屏（门 + 面板双轴）· 笔记本翻盖 · 手套箱门 · 吊扇灯盘
倾斜锁定 ×1钻床斜台（倾斜 + 锁柄）
连续转子 ×2离心榨汁机 · 自行车曲柄脚踏
多路调节 ×2健身车（座管 + 把手）· 灶台（四旋钮）
含连杆 ×1手套箱门（门 + 双限位连杆，唯一有耦合声明的）

十条里只有手套箱门有耦合声明，所以其余九条的 KF2 记 —（None）而不是 1.0。 这不是漏跑，是没有可测的东西。

1.3 载入配方（三个坑，不填就出错）

discardvisual="false"

Articraft 资产只有 <visual>。按 MuJoCo 默认会把它们全部丢掉， 编译出一个没有任何几何的模型。

<compiler discardvisual="false" inertiafromgeom="true" balanceinertia="true" strippath="false" fusestatic="false"/>

fusestatic="false" 同样重要：否则固定连杆会被合并，父子拓扑被改写。

距离一律 mj_geomDistance

实测 546 条真实资产里，有 <collision> 的是零个。 编译出来 contype = conaffinity = 0，mjData.ncon 永远是 0—— 基于接触点的碰撞检测在这里什么都返回不了。

mj_geomDistance 还不受父子过滤影响：MuJoCo 默认关掉有关节相连的父子碰撞， 而那恰好是最需要看的一对（门 vs 自己的柜体）。

<mimic> 要在编译前补回来

实测 7 条真实资产声明了 <mimic>，加载后 neq 全是 0—— 含传动比 −1 和 0.777778 的齿轮组、14 片联动百叶窗、反向对转碎纸机。

不处理的话 KF2 把这 7 条全判 0，理由是「没有约束」，可它们在 URDF 里写得完全正确。 那等于让资产替读取方的缺陷背锅。

两条走 XML 的路都不通，所以在编译前编辑 MjSpec。 URDF 的 q_dep = k·q_ind + c 与 polycoef 逐字段对应，翻译没有解释余地， 每次翻译都记进报告的 provenance 字段。

travel_scale 为什么量尺寸不量位移

原方案是「qpos 变了而可见部件不动」，但 P3 禁止渲染。

要抓的是：挂着正确的关节、正确的行程，但几乎没有几何。 位移测不出来——那个假部件把 0.18 m 老老实实走完了。 能测的是尺寸：滑 0.18 m 而只有 8 mm 宽的东西不是抽屉。

量部件自己不量刚性子树：那个假部件上挂了个真的 0.16 m 把手， 子树 0.39 m，而契约点名的部件只有 0.0139 m。

KF2 · 机械耦合保真度 —— 4 条

它不看几何，看模型自己的约束表。MuJoCo 的 eq_data 写成 q₁ = a₀ + a₁q₂ + …，与契约的 dependent = coefficient × independent + offset 逐字段对应，比较没有解释余地。

KF2 = mean_g 1[bound(g)] × 1[ max_q |r_g| ≤ ε_g ] bound 等式图上找 ind→dep 的最短链，链上每条都 active coefficient 沿链复合（斜率相乘、偏移累加），|ĉ−c|/|c| ≤ ε 且高次项 ≤ 1e−9 expected_dof n − (成员数 − active 图上的连通分量数) = expected_dof residual 33 个采样：中间关节按模型摆、依赖端按契约摆，读 efc_pos
原公式 mean 1[max|r| ≤ ε] 让最差的模型得满分。 残差只在模型真建了约束时才存在：生成器什么都不写 → 没有残差 → 空集取 max 让判断为真。加上 1[bound] 之后， gearbox_missing_coupling 从 1.00 变成 0.00。
bound 走链而不是只看直接约束：契约写 mechanism: any， 声明的是关系不是实现。手套箱把两根限位连杆都以 0.55 挂在门上，它们确实精确 1:1 在动， 只看直接约束会把一个正确的机构判成缺失（这条今天刚修，KF2 从 0.00 回到 1.00， 而金标准四件的分数一个没变）。

KF3 · 可行运动一致性 —— 四层采样 + 3 条

这个才是真的把物体摆到上千个姿态。是瞬移，不是运动：写 qpos → mj_forward → 量距离。不积分轨迹、不算接触力——那样结果会取决于质量阻尼和求解器迭代次数，而且不可复现。

按对计分，不按样本。1000 个姿态里 1 个深穿模是一对坏了， 除以样本数读成 0.99997——同一个缺陷会随采样密度移动四个数量级。姿态是证据，不是分母。
原方案的「运动有效性」大部分是恒真的：「状态可达」「轨迹连续」 「相对位姿符合关节语义」在编译好的 mjModel 上全是正向运动学自带的性质—— 把姿态写进 qpos 永远成功。所以「可达」被改写成 「能不能干净地停在那个状态」，那才是关于资产的问题。

三13 份标准资产：先证明检查本身对不对

缺陷是人造的、答案已知。这一步在跑真实资产之前完成。

为什么必须有这一环。拿真实资产跑出 0.87，这个数对不对没人知道。 最糟的情况是一条永远不会失败的检查：它在所有资产上输出通过， 看起来像「资产都挺好」，不像「代码坏了」——真实资产本来大部分就通过，两者长得一模一样。 没有已知的坏输入，这种检查根本看不出来。（原方案里就有四条是这样的。）

每条检查过三关：正确件上不响 · 自己的反例上响 · 别人的反例上也不响。 第三关是「一条诊断」和「烟雾报警器」的分界——什么坏了都响的检查没有诊断出父件错， 只诊断出「有东西不一样」。

反例存成对正确件的最小编辑（120 条逐检查预期写在清单里），所以缺陷是能读的 diff。 匹配不到任何东西的替换会直接报错——否则「反例」和对照件一模一样， 拿它测出来的检查看着可靠、实际什么都没查。
光是把正确件建出来就当场抓到 5 个 bug（真实资产一个都发现不了），其中一个是 对照件自己只靠 range 限位、没有几何挡住门——正是 required_contact 要抓的那类。

4.1 怎么读这张表

  • 三个分数各自独立，不能相加。KF1 = 通过数 / 不是 N/A 的数，KF2、KF3 同理。
  • — 表示该资产没有可测的声明，记 None 不是 1.0 也不是 0.0—— 空分母的指标不是「完美资产」，是「什么都没测到」。九条的 KF2 都是这种。
  • 各资产声明数不同（21–62 条），满分含金量不等。灶台的 1.00 建立在 31 条可判声明上， 钻床的 0.20 建立在 16 条上。
  • N/A 数值得单独看。吊扇 27 条 N/A（全场最多），因为四个叶片被合并进 rotor， 每条点名叶片的接触声明都绑不上——23 条接触声明只评了 5 条。
  • 这是诊断结果，不是最终得分。严格绑定下十条全部被 Gate 拒绝（部件粒度对不上，见第六节）。 表里的数字是打开诊断模式、对能绑上的部件评估、其余记 N/A 得到的。

五一次完整的判定（把上面串起来）

以金标准 swept_interference 为例——在门的扫过区域里放一个支架。

① 契约里的那两句
   joints:  {id: door_hinge, part: door, parent: cabinet_body, type: hinge,
             axis: {semantic: vertical}, anchor: {on_edge_of: door},
             range: {unit: rad, min: 0, max: 1.5708},
             states: {closed: 0.0, open: 1.5708}}
   contact_policy.forbidden:  {parts: [door, cabinet_body], state: all}
   contact_policy.required:   {parts: [door, cabinet_body], state: closed,
                               relation: stop_contact}      # 同一对，两个桶

② 载入   discardvisual="false" → 门板 geom 保住；无 <mimic>，不需要补

③ 采样计划   3 个自由度 → 1,119 个姿态
   门这一维在 ① 层拿到 33 个点：0° … 90°
   closed / open 在 ③ 层被精确访问
   door↔cabinet_body 这一对在 ② 层的包围盒判据下没被剪掉

④ 逐姿态量距离（mj_forward → mj_geomDistance）
   门开角    与柜体最小间距        来自哪一层
      0°      +0.00000            ③ 状态组合（closed）
     20°      +0.00000            ① 逐自由度
     25°      −0.00509            ① 逐自由度
     30°      −0.02791            ① 逐自由度   ← 最深
     35°      −0.01119            ① 逐自由度
     40°      +0.00000            ① 逐自由度
     90°      +0.00000            ③ 状态组合（open）

⑤ 三条检查各自结论
   KF3.forbidden_pair      判负 —— 最大穿透 0.02791 > 0.001，报出最坏构型 30°
   KF3.state_reachability  通过 —— closed 和 open 这两个状态本身是干净的
   KF3.required_contact    通过 —— closed 时门确实碰到柜体（有几何止挡）
   豁免：closed 那一批姿态上，door↔cabinet_body 的接触被 required 声明豁免，
         不算违规——这就是 precedence 字段的作用

这个例子说明三件事： ① 两个端点姿态都干净，只在中间撞——任何只查声明状态的做法都会判它完美； ② state_reachability 通过而 forbidden_pair 判负不矛盾， 它们问的是不同的问题：能不能停在那儿（能），和路上会不会撞（会）； ③ KF1 满分而 KF3 掉分——关节声明可以完全正确，几何仍然撞，这正是两条要分开的原因。

六想提的问题 · 暂定参数

① C5 归谁：去掉关节约束后几何撑不撑得住

KF1/KF2/KF3 加起来问不到这个问题。一扇声明了完美 revolute 关节、 一根合页几何都没有的门，三项全绿——求解器会无条件替资产执行关节约束。 而这是人工标注里失败最多的一项：425 条里 103 条，比第二名多十倍。 上面的实测已经证实：rec_stove_top_0002 P3 每一项 1.00、零失败，人工总评只有 3 分。

现有实现里有它的两块碎片（travel_scale、required_contact）， 但都没问到核心问题。做的话建议作为单独命名的扩展项、不进 Kinematic Profile，两张表并排报。

② 部件粒度不匹配的裁定，P1 / P2 是否一致

十条里生成器的部件划分普遍比提示词粗：曲柄脚踏把主轴、两个曲柄臂、链轮焊成一个 crank_assembly；灶台没有任何 burner link；吊扇把四个叶片合并进 rotor。

本组裁定：数目和提示词不一致即失败，Gate 拒掉它们是正确行为。 要组里定的是 P1/P2 是否采用同一裁定——不一致的话，同一个资产会在不同环节得到相反结论。

副作用值得单看：吊扇的 27 条 N/A 是全场最多，23 条接触声明只评了 5 条， 因为每条点名叶片的声明都绑不上。粒度问题卡住的，恰好是本来最该起作用的那类检查。

③ P0 的两个表达缺口

数量不定的复数
去掉 count 后无法表达「若干个键」		 笔记本资产有 48 个独立按键 link，契约一个都没声明 → 48 个真实自由度无人评估
由几何决定的比值
无法表达「比值由几何定而非声明定」		 手套箱门与限位连杆的比值提示词没给，只能声明「两根连杆彼此 1:1」—— 已因此引发过一次 KF2 误判（根因是 P0 说不出那个比值）

④ 十份契约需要第二个人核过

见 1.1。range_and_reference 触发 7/10、四处 π/2 全部落空， 就是这件事的直接证据。这需要复核契约，不是改检查。

⑤ Gate 接口

evo_p0p3/p3/gate.py 是替身，不是提案。真 Gate 落地时删掉， 接口是 Admission（binding: part id → body id）。 一处明说的偏离：G3 报告但不拦（合成惯量）。 严格绑定下十条全部被拒——Gate 若采用更宽松的绑定，P3 数字会变，需要在同一套绑定上重跑。
